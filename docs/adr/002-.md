# ADR 002: Use uv for environments and dependencies

- Status: Accepted
- Date: 2026-11-01

## Context

Up to v0.1 the project used pip with two hand-maintained files, `requirements.txt` (runtime) and `requirements-dev.txt` (test and lint tools). That setup caused concrete problems:

- **No lock file.** Only direct dependencies were pinned. Transitive dependencies resolved to whatever was newest on the day, so two installs weeks apart could differ.
- **Easy to get wrong.** An early `pip freeze > requirements.txt` listed 19 packages, most of them not imported by the code. A typo (`pytest=9.1.1`) in the dev file would only have shown up in CI.
- **Duplicated setup.** CI repeated installation steps that drifted from the files: a separate `pipx install ruff` (unpinned) and a bare `pip install pytest` next to the pinned versions.
- **Python version managed apart from dependencies** (see [ADR 001](001-python-version.md)).
- **The code became a package.** With a `src/` layout, the package must be installed into the environment for imports (and tests) to work, and plain `pip install -r` does not do that.

## Decision

Use **uv** as the single tool for the Python version, the virtual environment and dependencies:

- Dependencies are declared in `pyproject.toml`: runtime ones in `[project].dependencies`, development tools in `[dependency-groups]`.
- `uv.lock` is committed. It records the exact resolved versions of everything, transitive dependencies included.
- Commands run through `uv run`, locally and in CI.
- CI installs with `uv sync --locked`, which fails when `pyproject.toml` and `uv.lock` disagree.
- The package uses a `src/` layout and uv's build backend, so `uv sync` installs it into the environment.
- Version ranges in `pyproject.toml` (for example `>=`) say what is allowed; the lock file says what is used. Upgrades are explicit (`uv lock --upgrade`), reviewed in a pull request.

## Alternatives considered

1. **pip with `requirements.txt` files (status quo).** Familiar and universal, but no lock file for transitive dependencies and manual upkeep, which is where the problems above came from.
2. **pip-tools** (compile `requirements.in` into a locked `requirements.txt`). Fixes locking while staying close to pip. Rejected because it still leaves the Python version, the environment and the package install as separate steps and tools.

## Consequences

- Positive: reproducible installs. The same locked versions run on my machine and in CI, and a stale lock file fails the build instead of passing silently.
- Positive: one tool and one command set (`uv sync`, `uv run`) replace the `venv`, `pip`, `pipx` and Python-install steps. The CI file got shorter.
- Positive: runtime and development dependencies are separated in one file, so test-only tools stay out of what ships.
- Mitigation: `pyproject.toml` uses standard project metadata and dependency groups, so moving to another tool is possible; only the lock file format is uv-specific.
- Negative: the lock file can create merge conflicts and large diffs. Accepted: the diff is also the review surface for dependency changes.
